# 작업 내역 — 2026-08-24

IDIS 임직원 복리후생 신청 시스템. 사용자 영역(로그인 → 폼 목록 → 신청 → 완료 → 신청 내역)을
한 줄로 관통시키고, 피그마 시안 기준으로 전체 화면 테마를 통일했다.

---

## 1. 로그인

`login.html`에 폼은 있었지만 `POST /login`을 받는 핸들러가 없어 동작하지 않는 상태였다.

**인증 방식**: 이름 + 전화번호로 재직 중인 임직원 조회. 전화번호는 숫자만 남겨 비교하므로
DB에 하이픈이 있든 없든 매칭된다.

| 파일 | 역할 |
| --- | --- |
| `auth/AuthController` | `GET/POST /login`, `POST /logout` |
| `auth/AuthService` | 이름+전화번호 인증, `Optional<LoginUser>` 반환 |
| `auth/LoginForm` | 폼 바인딩 DTO |
| `auth/LoginUser` | 세션 저장용 record (LAZY 프록시 직렬화 회피) |

에러 표시는 `redirect:/login?error` + `th:if="${param.error}"` 한 줄로 처리했다.
`@Valid`/`BindingResult` 없이도 `AuthService`가 blank를 걸러내므로 빈 값도 같은 경로로 간다.

> **설계 메모**: 초기에 인터셉터·세션 상수·리다이렉트 복귀까지 구현했다가, 사내 팀 단위
> 내부 도구에 과한 구조라는 판단으로 전부 걷어냈다. 현재 로그인 검사는 각 핸들러에서
> `currentEmployee(session)` 한 줄 호출로 처리한다. 관리자 라우트가 늘어나면 그때
> 인터셉터를 다시 검토한다.

## 2. 폼 목록 + 시드 데이터

관리자 화면보다 사용자 화면을 먼저 만들기로 했다. 이유:

- 관리자 대시보드(응답률·응답 목록)는 **응답 데이터가 있어야** 의미가 있는데, 응답은
  사용자가 제출해야 생긴다.
- `Question.config`가 JSON 컬럼으로 열려 있는데 무엇이 들어가야 할지 미정이었다.
  사용자 렌더러를 먼저 만들면 그게 실측으로 정해진다.
- `FormRepository`/`ResponseRepository`에 이미 사용자 플로우용 메서드가 준비돼 있었다.

**`GET /forms`** — `FormStatus.OPEN` + `Form.isOpen()`(기간) + `FormTarget.includes(EmployeeType)`
로 필터링, 마감 임박순 정렬, 신청 완료 배지 표시.

대상 구분과 재직 여부는 **세션이 아니라 DB에서 다시 읽는다**. 세션 타임아웃이 30일이라
그 사이 인사 변동이 있으면 세션 값이 낡기 때문이다.

**시드 데이터** (`seed/sample-form.sql`) — 필터가 실제로 동작하는지 확인 가능하도록 구성:

| --- | --- | --- | --- | --- |
| 1 | 2026년 추석 선물 신청 | ALL | OPEN | 4 |
| 2 | 2026년 생일 케이크 신청 | ALL | OPEN | 2 |
| 3 | IDIS 창립기념품 신청 | **DIRECT** | OPEN | 1 |

## 3. 폼 작성 / 제출 / 완료

**렌더러 지원 타입**: `SHORT_TEXT`, `LONG_TEXT`, `NUMBER`, `DATE`, `SINGLE_CHOICE`,
`DROPDOWN`, `ADDRESS`, `SECTION`.
미지원 타입(`IMAGE_CHOICE`, `MULTI_CHOICE`, `SCALE`, `FILE`)은 조용히 빠지지 않고
**"아직 지원하지 않는 질문 유형입니다"로 명시 표시**한다.

**주소 입력**: 실제 배송에 쓰이는 주소라 다음 우편번호 API를 붙였다.
`Answer.value`에 `{"zipcode":"06236","address":"...","detail":"5층"}` 형태로 저장해
배송업체 전달용 엑셀에서 우편번호를 분리해 뽑을 수 있다.

**제출/수정**: `(form_id, emp_no)` 유니크 제약으로 1인 1응답. 기존 응답이 있으면
`clearAnswers()` 후 답변만 교체하므로 중복 레코드가 생기지 않는다.

### 이 과정에서 잡은 문제 2건

**Jackson 패키지 변경** — Spring Boot 4는 Jackson 3(`tools.jackson.*`)을 쓴다.
`com.fasterxml.jackson.databind`로는 컴파일되지 않으며, `JacksonException`이
`RuntimeException`이 되어 checked 예외 처리가 사라졌다.

**필수 검증을 트랜잭션 안에서 예외로 던지면 500** — 롤백 후 Hibernate 세션이 닫혀
화면을 다시 그릴 때 `Question.choices` 지연 로딩이 `LazyInitializationException`으로 터진다.
검증을 트랜잭션 밖(`ResponseService.validate`)으로 분리하고, 저장과 **같은 `buildAnswer`**를
쓰게 해서 "검증은 통과했는데 저장은 비어있는" 불일치를 막았다.

부수적으로 선택지 조회를 `ChoiceRepository` 대신 `question.getChoices()`에서 찾도록 바꿨다.
소속 검증이 자동으로 되고(남의 질문 선택지 위조 차단) DB 조회도 사라진다.

## 4. 신청 내역

`/forms` 목록은 진행 중인 폼만 보여주므로 **마감되면 신청 이력이 화면에서 사라지는** 구멍이 있었다.

**`GET /responses`** — Response 기준으로 조회해 상태 필터를 두지 않는다.
마감되거나 대상에서 빠진 폼도 이력에 남는다.

`GET /forms/{id}`도 **편집 가능 여부와 조회 가능 여부를 분리**했다. 마감된 폼이라도
신청 이력이 있으면 읽기 전용(모든 입력 `disabled`, 제출 버튼 숨김)으로 열린다.
`POST`는 여전히 편집 가능한 폼만 받으므로 URL 조작으로는 수정할 수 없다.

## 5. 최적화 / 버그 수정

**"수정됨" 표시가 양방향으로 틀려 있었다.** `updatedAt > createdAt` 비교였는데:

- 최초 제출만 해도 42ms 차이로 `updatedAt`이 밀려 **수정 안 했는데 "수정됨"**이 뜨고
- 실제 수정에서는 답변이 `mappedBy` 관계라 response 행이 UPDATE되지 않아 **감지가 안 됨**

→ `Response.editedAt` 컬럼과 `markEdited()`를 추가해 기존 응답 수정일 때만 찍도록 변경.

| 항목 | 내용 |
| --- | --- |
| 중복 `save()` 제거 | 영속 상태라 커밋 시 자동 flush. 제출마다 나가던 불필요한 UPDATE 제거 |
| N+1 제거 | `findMyResponses`가 응답마다 form을 지연 로딩 → `join fetch` 쿼리 하나로 |
| 미사용 필드 제거 | `MyResponseView.formStatus` |

## 6. 디자인 — 피그마 시안 적용

피그마 `idis-login-variant`(우측 로봇) 시안으로 로그인 페이지를 구현했다.

- 민트 패턴 헤더 + 로봇, 아이콘 들어간 입력창, "또는" 구분선
- **"로그인이 안 되나요?"** 버튼 → 관리자 문의 모달(`<dialog>`)
- 에셋 6종을 로컬 저장(피그마 URL은 7일 후 만료). 원본이 무거워 표시 크기 2배로 리사이즈
  (헤더 배경 1.2MB → 146KB, 로봇 537KB → 55KB)

> 하단 "안전한 정보 보호" 배너는 불필요하다는 판단으로 제거. 관련 CSS와 `icon-shield.svg`도 정리.

## 7. 전체 테마 통일

`login.css`는 피그마 토큰인데 `forms.css`는 예전 값이라 갈라져 있었다.
공통 `theme.css`를 만들어 토큰·컴포넌트를 한 곳에 모으고, 페이지별 CSS는 고유한 것만 남겼다.

| | 이전 (forms) | 통일 후 |
| --- | --- | --- |
| 본문 회색 | `#58595B` | `#6B7280` |
| 보조 회색 | `#A7A9AC` | `#9CA3AF` |
| 경계선 | `#E3E6E9` 1.5px | `#E5E7EB` 1px |
| 컨트롤 radius | 10~14px 제각각 | 8px (카드 12, 모달 16) |
| 주요 버튼 | 54px / weight 700 | 51px / weight 600 |

**토큰만 맞춰서는 화면 인상이 그대로였다.** 로그인의 시각적 정체성인 **민트 헤더 밴드**를
내부 화면으로 옮겨야 했다.

```
┌──────────────────────────┐
│ [IDIS]    신청 내역 로그아웃 │  ← 민트 패턴 (로그인과 같은 이미지)
│ 홍길동님, 안녕하세요        │
│ 신청 가능한 복리후생        │
├──────────────────────────┤  ← 흰 카드가 20px 위로 겹침, 상단 radius 20
│   [카드] [카드] [카드]      │
└──────────────────────────┘
```

로봇 캐릭터는 내부 화면에 넣지 않았다 — `aa.md`에 "캐릭터를 모든 화면에 반복적으로
사용하지 않는다"고 명시돼 있어 로그인·완료·빈 화면에만 유지.

### 후속 수정 2건

**패턴 위 글자 가독성** — 패턴 이미지의 바탕색이 정확히 `#F1F8FA` 단색이라, 그 색으로
페이드시켜 이음매 없이 글자 영역만 평평하게 만들었다. 패턴은 상단 바 뒤 78px까지만 보인다.

```css
background:
    linear-gradient(to bottom, rgba(241,248,250,0) 30px, var(--head-bg) 78px),
    url("/image/login-header-bg.png") center top / cover no-repeat;
```

**빈 화면 이미지** — `domi.png`가 135×129 저해상도인데 72px로 띄우고 `opacity: .8`까지
먹여 바래 보였다. 360px 고해상도 로봇을 민트 원 안에 넣는 방식으로 교체
(`login-robot.png` → `robot.png`로 파일명 정리).

## 현재 상태

### 라우트

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| GET | `/` | 로그인 여부에 따라 `/forms` 또는 `/login` |
| GET · POST | `/login` | 로그인 |
| POST | `/logout` | 로그아웃 |
| GET | `/forms` | 신청 가능한 복리후생 목록 |
| GET · POST | `/forms/{id}` | 폼 작성 / 제출·수정 |
| GET | `/forms/{id}/complete` | 신청 완료 |
| GET | `/responses` | 신청 내역 |

### 화면

`login.html` · `forms.html` · `form-detail.html` · `form-complete.html` · `responses.html`

### 스타일

`theme.css`(공통 토큰·컴포넌트) → `login.css` / `forms.css`(페이지 고유) 순으로 로드.

### 테스트 계정

| 사번 | 이름 | 전화번호 | 구분 | 권한 |
| --- | --- | --- | --- | --- |
| 20240001 | 홍길동 | 010-1234-5678 | DIRECT | EMPLOYEE |
| 20240002 | 김관리 | 010-9876-5432 | INDIRECT | ADMIN |

### 실행

```
cd employee_benefits/idis
./gradlew bootRun
```

MySQL이 `localhost:3306/idis`에 떠 있어야 한다. 접속 후 `http://localhost:8080/login`.

시드 폼 데이터가 필요하면:

```
mysql -u root -p --default-character-set=utf8mb4 idis < seed/sample-form.sql
```
